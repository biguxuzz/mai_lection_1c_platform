# Лекция 6: Собственный вид доступа и разбор работы ограничений (БСП)

**Продолжительность:** ~60 минут (по объёму стенограммы)  
**Целевая аудитория:** Студенты 3 курса, курс по библиотеке стандартных подсистем  
**Курс:** Библиотека стандартных подсистем  

**Источник занятия:** транскрипция `БСП_11_Свой_вид_доступа_и_разбор_работы.txt` (демонстрация на демоконфигурации БСП; документ **«Реализация товаров и услуг»**, виды доступа по **организации** и по **складам** в табличной части).

## Цель лекции

Показать, как ввести **собственный вид доступа**, когда стандартного набора недостаточно: пример — ограничение документа **«Реализация товаров и услуг»** не только по **организации**, но и по **складу** в **табличной части**. Разобрать шаги: переопределяемый метод **при заполнении видов доступа**, **определяемые типы** значений доступа, **ограничение в модуле менеджера документа** (`ЗначениеРазрешено`, `ДляВсехСтрок`, уточнения для пустой ТЧ и пустых ссылок), включение вида в **поставляемый профиль**, настройка **групп доступа** и проверка в режиме предприятия. Завершить **обзором механизма**: наборы групп доступа, **ключи доступа**, регистры сведений, «пустой» разрешённый набор; **программный интерфейс** подсистемы и отладка **RLS** через выгрузку запроса в XML.

## Необходимые предзнания

- Подсистемы «Пользователи» и «Управление доступом» (профили, группы доступа, ограничение доступа на уровне записей)
- Документы, табличные части, определяемые типы
- Переопределяемые модули БСП

---

## План лекции

### 1. Задача: свой вид доступа по складам

Если нужного **вида доступа** в поставке БСП нет, его добавляют программно. Пример: для документа **«Реализация товаров и услуг»** нужен отбор не только по **организации**, но и по **складу** в **табличной части** «Товары».

Для регистрации нового вида вызывают одноимённый метод из **переопределяемого модуля управления доступом** (в транскрипте — «модуль управления доступом МП»): **`ПриЗаполненииВидовДоступа`**. Для типовых сценариев определение вида доступа настраивается **быстро**, по образцу из документации/демо.

### 2. Объявление вида доступа «Склады»

В процедуре заполнения видов доступа (по первому примеру из шаблона БСП):

- **Имя** вида доступа, например **`Склады`**.
- **Представление** для администратора.
- **Тип значения** — ссылка на справочник **«Склады»** (или иной тип, задающий гранулу доступа).

### 3. Группы значений доступа (по желанию)

**Группы** нужны, когда значений много и их удобно объединять: создаются отдельные справочники-группы. В демоконфигурации пример — **демо-группы доступа к номенклатуре**; у номенклатуры в реквизите указана группа **или** табличная часть **«Группы доступа»** с множеством групп на один объект — это **уменьшает число ключей доступа** и **ускоряет пересчёты**. Нюансы — в документации БСП. В рассматриваемом примере **группы не используются** (второй пример из шаблона не нужен).

### 4. Определяемые типы «Значение доступа»

После добавления нового типа в справочник **видов доступа** нужно расширить **определяемые типы** (в транскрипте — **«Значение доступа»**, **«Значение доступа объекта»**):

- в состав **значения доступа** включить тип **СправочникСсылка.Склады** (или актуальное имя в конфигурации);
- в **значение доступа объекта** — при необходимости включить **`Склады.Объект`** (как в демо).

### 5. Поставляемый профиль

Новый вид доступа добавляют в **поставляемый профиль** (в примере имя вида в профиле — **`Склады`**, согласовано с объявлением).

### 6. Ограничение в модуле менеджера документа

В **`ПриЗаполненииОграниченияДоступа`** модуля менеджера документа **«Реализация товаров и услуг»** добавляют условие по складу:

- если достаточно, чтобы документ был разрешён при **хотя бы одном** разрешённом складе в строках — используют конструкцию в духе **`ЗначениеРазрешено(Товары.Склад)`** (точные имена полей — по метаданным);
- если нужно, чтобы были разрешены **все** строки — **`ДляВсехСтрок`** с уточнением по складу.

**Пустая табличная часть:** в конструкции **`ЗначениеРазрешено`** для пустой ТЧ оператор может вернуть **`NULL`** — его уточняют как **истину**, чтобы разрешить чтение/изменение документов с пустой ТЧ (если это допустимо по смыслу).

**Черновик / пустой склад в строке:** для пустой ссылки на склад в строке можно задать уточнение **пустая ссылка как истина**, чтобы разрешить работу с незаполненным складом до оформления.

После изменений — **обновление информационной базы** с отметкой **«запустить с отключением блокировки»** / ключом доступа к обновлению (формулировка в транскрипте — запуск обновления ИБ с нужными параметрами).

### 7. Администрирование: профиль и группы доступа

В **«Администрирование» → Пользователи и права → Профили и группы доступа»**:

- у профиля (в примере — **«Продавец»**) в ограничениях появляется новый вид доступа **«Склады»**;
- по ссылке — **группы доступа**; для группы **«Наши продавцы»** задают разрешённый склад (например, **«Склад магазина»**);
- для наглядности копируют группу, меняют участника, создают пользователя (например, тестировщик), задают другой склад (**«Основной»**), переименовывают группу (например, **«Продавцы основного склада»**).

### 8. Проверка в режиме 1С:Предприятие

Под пользователем с группой **«Наши продавцы»**, организацией **«Ромашка»** и складом **«Склад магазина»**:

- при снятом флаге **«Только мои документы»** виден документ, где и организация, и склад в строке попадают под ограничение;
- **новый документ** без доработки уточнений по организации может дать ошибку **недостаточности прав** — пока **пустая ссылка по организации** не уточнена как разрешённая, документ недоступен;
- после выбора доступной организации и записи — уточнения по пустой ссылке работают;
- склад **«Основной»**, не входящий в разрешённые для пользователя — **запись невозможна**; смена на **«Склад магазина»** — документ записывается.

### 9. Как это устроено внутри (ключи и наборы)

- В справочнике **«Наборы групп доступа»** по **уникальному идентификатору пользователя** находится элемент; в нём — **разрешённый набор групп доступа** — условно «уникальный» набор прав пользователя; пользователи с одинаковым набором групп (например, **«Работа с папками файлов»** + **«Наши продавцы»**) получают **тот же** разрешённый набор групп доступа.
- Регистр сведений **«Ключи доступа наборов групп доступа»**: связка **набор групп доступа** (та группа, что настроена у пользователя) и **ключи доступа**, которые эта группа выдаёт.
- **Ключ доступа** описывает объект в терминах ограничений: для документа — тип **«Реализация товаров и услуг»**, в «шапке» — значение вида доступа **«Организация»**, в табличной части (в примере — **табличная часть 1 / товары**) — реквизит **«Склад»** и конкретное значение (например, **«Склад магазина»**). По ключу видно, что группа даёт право **добавления** и **изменения** для таких документов.
- Регистр **«Ключи доступа к объектам»** позволяет по объекту найти связанные ключи (обратный переход).

**Пустой разрешённый набор групп доступа:** при разборе ключей встречается ситуация, когда используется **пустой** набор — это **сокращает количество записей**: для всех наборов групп доступа, выдающих доступ к документу, один и тот же ключ может быть доступен, поэтому не всегда нужен конкретный «разрешённый набор», найденный строго по пользователю (детали — в логике БСП на ИТС).

### 10. Программный интерфейс и отладка RLS

В подсистеме управления доступом для разработки в основном используется **один модуль** — **серверный модуль управления доступом** (программный интерфейс).

Типичные методы проверки прав (имена по смыслу лекции):

- **`ЧтениеРазрешено`**, **`ИзменениеРазрешено`** — без исключения;
- варианты, которые **вызывают исключение** при запрете — для явной остановки при нарушении прав.

Поставив **точку останова** на таком методе, можно попасть в **запрос**, который реализует **RLS** (ограничение на уровне строк). Его можно выгрузить через метод общего модуля в духе **`RLSЗапросВСтрокуXML`** и отладить в **консоли запросов** — в тексте видны связи таблиц и условий, о которых шла речь в курсе.

На этом **обзор подсистемы управления доступом** в рамках темы считается завершённым.

## Резюме

1. Собственный **вид доступа** добавляют в **`ПриЗаполненииВидовДоступа`** переопределяемого модуля управления доступом.  
2. Задают имя, представление, тип значения (часто ссылка на справочник); **группы значений** — опционально, для сжатия ключей на больших объёмах.  
3. Обновляют **определяемые типы** значений доступа и объекта доступа.  
4. Вносят вид в **поставляемый профиль** и пишут **ограничение** в модуле менеджера документа с учётом **пустой ТЧ** и **пустых ссылок**.  
5. После обновления ИБ настраивают **группы доступа** и проверяют сценарии.  
6. Внутренняя модель: **наборы групп доступа**, **ключи доступа**, регистры; для отладки — **RLS** через XML-строку запроса.
