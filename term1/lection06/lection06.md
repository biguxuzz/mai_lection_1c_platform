## Часть 1. Поставка конфигурации

### Зачем нужна поставка

- Если вы **разработчик решения**, есть несколько способов передать конфигурацию заказчику.
- Для **небольших** конфигураций (в т.ч. учебных) можно выгружать полный **`.cf` / `.cfu`** (в стенограмме «CFX» — устная формулировка) — проблем обычно нет.
- Когда решение **объёмное**, много кода и **бинарных** вложений (картинки, схемы и т.д.), удобнее штатный механизм **поставки** из конфигуратора.

### Создание файла поставки

- Поставка создаётся из конфигуратора; **номер версии** подтягивается из **свойств конфигурации**.
- **Первая поставка** — как правило **полная**; система может сразу предложить создать **файл разницы** (`.cfu`), но если сравнивать не с чем — разностный файл может быть не нужен.

### Развёртывание у заказчика

- Создаётся отдельная ИБ, конфигурация **загружается из файла поставки** («открыть / загрузить конфигурацию из файла»).
- Конфигурация из поставки по сути **«на замке»** по сравнению с произвольной выгрузкой: прямое редактирование ограничено политикой **поддержки**.

### Полная поставка и разница (`.cfu`)

- **CFU** обычно **меньше по размеру**, чем полная поставка.
- На проектах внедрения, когда в базе заказчика уже **много данных**, накат **последнего обновления** из **разностного** файла часто **быстрее**, чем перезаливка полной конфигурации.
- Продуктивная база не должна меняться «вручную» в обход регламентов — только через **обновления** по согласованной процедуре.

### Поддержка и «замки»

- У конфигурации, взято из поставки, настраивается **поддержка** (конфигурация поставщика).
- Если **не включено** изменение снятых с поддержки объектов, объекты остаются **под замком** — реквизиты, типы, табличные части **не меняются**, пока для объекта (или иерархии) явно не разрешены изменения.
- Для **подчинённых** объектов разрешение можно выдавать выборочно.
- Частая ошибка — **снять замки со всего** подряд «по умолчанию»; для типовых продуктов так делать **не рекомендуется**.

### Изменения у поставщика и у заказчика (сюжет лекции)

- После включения возможности изменений заказчик может править, например, **модули** (менеджера, объекта, проведения).
- На стороне разработчика в «своей» конфигурации добавлялись новые объекты (в т.ч. документы **поступления / списания денежных средств**, подсистема **«Казначейство»**), менялась логика.
- Для следующего релиза создаётся поставка **с предыдущей версией** для построения **разницы** — у заказчика выполняется **обновление конфигурации** из файла обновления.

### Нумерация версий (практика)

- В типовых и отраслевых решениях есть **общепринятая схема** разрядов версии.
- **Последний разряд** — часто мелкие исправления, без тяжёлой смены логики и **реструктуризации** данных.
- Если добавили только новые объекты и не ломали существующие данные — можно двигать **предпоследний** разряд (в примере на лекции).
- Если нужны **обработки переноса** исторических данных, меняют **второй** разряд; **первый** — при глобальных изменениях (смена подходов, форм и т.д.).

### Обновление на стороне заказчика

- Выбор файла обновления; размер **CFU** заметно меньше полной поставки.
- При накате обновления: опция **заменить** изменённые модули кодом поставщика или **сохранить** доработки заказчика; при включённой поддержке доступно **сравнение** метаданных.
- Сценарий **параллельных** правок: у заказчика и у поставщика менялись одни и те же объекты (переименование реквизитов, типы) — требуется **сопоставление объектов**, иногда правка **вручную**; при невозможности наката — **обработки переноса данных** или осознанное **удаление** своих временных реквизитов и выравнивание под поставщика.
- Если нужно **полностью вернуться** к конфигурации поставщика — загрузка **поставки от поставщика** целиком; настройки поддержки снова как у типовой поставки.

### Ошибка «не та предыдущая версия»

- Если в CFU **не указать** нужную предыдущую версию или указать несовместимую, обновление может **не примениться** (в примере — сообщение, что файл рассчитан на версию **1.0.1**).
- Выход: выпустить корректную поставку или, при необходимости, обновиться с **полного** файла конфигурации.

### Демонстрация: регистры и проведение (контекст поставки)

- В ходе демо добавлялись **справочники** (в т.ч. **банковские счета** с маской кода), документы казначейства, **регистры накопления**: **взаиморасчёты**, **денежные средства**; настраивались **регистраторы** и **конструктор движений** (приход/расход по смыслу операций).
- Подчёркивалось: при выпуске поставки **не забывать повышать номер версии** — полезная привычка и для собственной разработки.

### Типовые конфигурации и номер поставки

- При внедрении **крупной типовой** конфигурации **нельзя произвольно менять** схему нумерации «как захотелось»: механизмы обновления завязаны на **номер основной поставки**.
- Варианты: вести **свою** нумерацию выпусков вручную (неудобно) или сделать свою конфигурацию **основной поставкой** (переименование, подсистемы) — это **большой объём** работ по сопровождению переходов между релизами.

## Часть 2. Групповая разработка: хранилище конфигурации

### Роль хранилища

- Исторически основной инструмент командной работы в 1С — **хранилище конфигурации** (в учебной поставке под Windows оно может идти в комплекте; в варианте для WSL в примере лекции **отдельно не собиралось**).

### Линейность и Git

- Современный стандарт для кода — **Git**; раньше использовались **CVS** и аналоги с **ветвлением**.
- Хранилище 1С в классическом виде — скорее **линейная** история: **веток нет**, можно откатиться к предыдущему состоянию, но не вести параллельные ветки как в Git.

### Создание и подключение

- Хранилище создаётся из конфигуратора (**создать хранилище**, путь, пользователь-администратор); появляется режим **замков**.
- Второй разработчик: отдельная ИБ, **файловая** тоже может подключаться к хранилищу.
- Чтобы не набирать данные вручную, можно загрузить **`.dt`** или работать с обезличенной копией клиентской базы.

### Пользователи хранилища

- Нельзя подключить второго «администратора» тем же составом учётных записей, что и у создателя, без учёта привязки баз — в **администрировании хранилища** добавляются **пользователи**, видно, кто с какой базой связан.

### Захват корня и комментарии

- Чтобы добавить **новый объект**, нужно захватить **корень конфигурации** — **только один** разработчик может держать корень; время захвата нужно **минимизировать**.
- Не злоупотреблять **рекурсивным** захватом без необходимости.
- Приём: быстро создать «заготовку» объекта, **поместить** в хранилище и **освободить** корень.
- В комментарии к помещению указывать **задачу** (тикет), чтобы по истории было понятно назначение изменений.

### Администрирование

- Видно, **кто захватил** какие объекты; при болезни разработчика захват можно **принудительно отменить**.

### Интеграции и промышленный контур

- Упоминались **OneScript**, выгрузка из хранилища в **Git**, **CI/CD**, **SonarQube**, проверка стандартов, автотесты.
- На крупных проектах — **каскад хранилищ**: разработка → тест → **предпрод** → **прод**; **релиз-менеджер** переносит проверенные задачи.
- Обычно выделяют **четыре контура**: разработка, тестирование, предпрод, прод; на предпроде — регрессия по задачам, риск **неконсистентности данных** заказчика при «правильной» по коду задаче.
- Возможны схемы «**у каждого разработчика своё хранилище**» с последующей синхронизацией — сложнее.

### Размещение и лицензии

- Файл хранилища — по сути **отдельная база 1С**; можно разместить на сервере (**Apache** и т.д.); **отдельная лицензия на хранилище** как на рабочую ИБ не требуется — её не запускают как базу с пользовательскими данными.
- **Одновременно** с одной и той же файловой базой конфигурации в конфигураторе работает **один** сеанс; у каждого разработчика — **своя** копия базы, в общую тестовую подтягиваются изменения из хранилища (вручную или по пайплайну).

### Поставка из хранилища и нумерация

- На **предпроде** релиз собирают через **поставку**; при работе на базе **типовой** конфигурации снова важно не ломать **нумерацию** поставки вендора — см. раздел про типовые обновления выше.
- В демо: захват **корня** администратором для смены **номера релиза** перед созданием поставки.

## Резюме по записи

1. **Поставка:** полный файл и **CFU**; версия из свойств; у заказчика конфигурация на **поддержке** и с **замками**.  
2. **Обновление:** предыдущая версия для диффа; размер; опции слияния кода; сопоставление объектов при коллизиях.  
3. **Версии:** смысл разрядов; миграции данных при серьёзных изменениях.  
4. **Демо:** казначейство, документы, регистры, проведение — на фоне сценария выпуска.  
5. **Хранилище:** линейная история, захват **корня**, комментарии и задачи, администрирование, контуры и пайплайны, EDT/напарник как внешний контекст.
