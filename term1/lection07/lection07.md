## Часть 1. Оформление: подсистемы и картинки

### Общие картинки и ZIP

- Иконки добавляются в **общие картинки**; в архиве — **несколько ZIP** под разные разрешения, **распаковывать все не нужно**: один архив распаковать, дальше в конфигураторе **подключать ZIP** как источник.
- Подсистемам назначались картинки: **закупки**, **продажи**, **администрирование**, **справочники**, **казначейство**, **сервис** и т.д. (набор зависит от варианта учебной конфигурации).

### Главный раздел и настройка области

- Отдельно настраивалась **картинка основного раздела** («главное» / карман) через свойства стиля или связанные настройки интерфейса.
- **Трюк с панелью:** если панель раздела занимает много места, в **настройках раздела** можно **показывать картинку** так, чтобы интерфейс был компактнее.

### Версия и поставка

- При любых изменениях напоминание **менять номер версии** в свойствах конфигурации (в т.ч. при «косметике» — добавляли **последний разряд** версии).

## Часть 2. Задачи

### Связь с бизнес-процессами

- **Задачи** могут существовать **без** бизнес-процесса; **бизнес-процесс без задач** — нет (по смыслу платформы в контексте лекции).

### Реквизиты адресации и форма списка

- Для задачи добавлен реквизит адресации **«Исполнитель»** (тип — пользователь).
- Создана **форма списка задач**, выведена на **начальную страницу** через **рабочую область** (в примере убрали лишнюю колонку макета, оставили одну).

### Отбор и «чужие» задачи

- В списке сначала были видны **все** задачи, в т.ч. **чужие** и **выполненные** — для списка добавлен **отбор: Выполнено = Ложь**.
- Для фильтра по исполнителю в адресации настроены **основная адресация** и **текущий исполнитель** (связь с **параметром сеанса** «текущий пользователь»); у списка появилась **виртуальная таблица** «задачи по исполнителю».

### Права

- Права в интерфейсе **управляемого приложения** выглядят иначе, чем в классическом варианте; для роли **«Продавец-закупщик»** (пример) на объект **Задача** выданы **интерактивное добавление**, **выполнение**, **активация**, **пометка на удаление** и др. — **матрица доступа** по объекту.
- Без прав под пользователем список задач **пустой** — на лекции это диагностировали и исправили.

## Часть 3. Бизнес-процессы: адресация по ролям

### Зачем регистр сведений

- Назначать задачи **каждому пользователю** вручную неудобно при больших отделах; вводится **роль исполнителя** на уровне процесса.
- Создан **регистр сведений** «адресация задач» **без ресурсов**, измерения: **исполнитель**, **роль** (роль — ссылка на **перечисление** «роль исполнителей»: закупщик, продавец, казначей и т.п.).
- Смысл пересечения в регистре: задача адресуется **роли**, а **конкретный пользователь** из этой роли берётся из заполненных строк регистра (кто из роли **первым** выполнит — по смыслу сценария на лекции).

### Связь задачи и регистра

- У **задач** и у **бизнес-процесса** добавлены реквизиты адресации, в т.ч. **«Роль»**, связь с регистром через **связи параметров** (тип связи по измерениям **роль** / **исполнитель**).
- На регистр адресации выданы **права на просмотр** нужным ролям; проверяли **параметры сеанса** (текущий пользователь).

### Карта маршрута

- Бизнес-процесс в конфигураторе: **карта маршрута** — обязательны **старт** и **как минимум одно завершение**.
- Пример **«Процесс продажи»**: сначала этап **закупки** (роль закупщика), затем **продажи**, затем **ветвление «требуется ли оплата»** — если да, задача **казначею**, если нет — сразу **завершение**.
- Условие ветвления вынесено в **реквизит БП** (булево **«Требуется оплата»**), проверка условия в схеме возвращает результат для развилки.

### Права на бизнес-процесс и запуск

- Для проверки временно выдали **полные права** на процесс (в учебных целях без детальной матрицы).
- Процесс не был виден в интерфейсе, пока **не добавлен в подсистему** — запускали через **«Функции для технического специалиста»**.

### EDT и конфигуратор

- В **EDT** редактор карты маршрута «ведёт себя хуже», чем в **конфигураторе**; при ошибке «процесс содержит ошибки» схему **дорисовали в конфигураторе**.
- В конфигураторе видно, **какие роли** использованы в точках маршрута; в EDT такой наглядности нет — после правок в конфигураторе нужен **импорт конфигурации в EDT** (или согласованный порядок работы), иначе расхождение версий.

### Заполнение адресации и прохождение сценария

- При пустом регистре адресации задачи **не появляются** — вручную заполнили соответствие **пользователей и ролей** (администратор также как закупщик, продавец, казначей для демо).
- Пошагово выполняли задачи под **закупщиком**, **продавцом**, **казначеем**; процесс **успешно завершился**.

## Часть 4. Наглядность: форма бизнес-процесса со схемой

- Добавлена **форма БП**, реквизит **«Схема процесса»** типа **графическая схема**, выведена на форму без лишнего заголовка.
- Команда **«Обновить схему»** (картинка на кнопке), обработчик с **вызовом на сервере**: чтение объекта, получение **карты маршрута**, подстановка в схему.
- Вызов обновления также из **«При создании на сервере»** формы, чтобы схема отрисовалась **сразу при открытии**.
- Нюанс **версии объекта:** после выполнения задач объект БП на сервере **обновился** (например, признак **завершён**), а открытая форма держала **старую версию** — при записи возможна **ошибка перезаписи**; в учебном сценарии показали, что маршрут на схеме отображается, но **перечитывать** форму/объект нужно осознанно.

### Итог по БП

- Встроенный БП в учебную конфигурацию — **плюс**; в **EDT** со схемами работать **аккуратно** (в лекции — «лайтовый» вариант, бывают сложнее).

## Часть 6. Ввод на основании (приход товара → списание денежных средств)

### Конструктор и связи документов

- Для цепочки документов использован **конструктор ввода на основании**: основание — **приход товара**, заполняются **контрагент**, **сумма** и др.; табличные части в конструкторе **не копируются** автоматически — доработка вручную при необходимости.
- У документа-основания в свойствах: **«является основанием»** → целевой документ; у принимающего документа — модуль/конструктор **ввода на основании**.

### Команда в форме списка

- Для появления команды **«Создать на основании»** в интерфейсе доработана **форма списка** документа-основания (в т.ч. переход в нужный **раздел** интерфейса — «закупки»).

### Синхронизация EDT и проверка движений

- После правок снова **импорт из конфигуратора в EDT** и проверка в режиме **1С:Предприятие**.
- Демо: сумма подтянулась, **банковский счёт** не заполнялся (в базе не создавали); проверка **регистра взаиморасчётов** выявила **ошибку знака** движений у **прихода товара** — в модуле объекта для взаиморасчётов исправили на **расход** (вместо прихода).
- Замечание: при работе с **платформой 8.5** и связкой **EDT / .dt / импорт** возможны **несостыковки** применения изменений — **проверять** результат; разбор **автотестов и проверок** — на **следующем семинаре**.

### Инструкция студентам

- Если делали только в конфигураторе: у основания добавить **«является основанием»**, у принимающего документа настроить **конструктор ввода на основании**.
