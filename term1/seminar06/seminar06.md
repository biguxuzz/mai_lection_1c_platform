## Часть 1. Запуск EDT и рабочая область

### Доступ и иконки

- Логины/пароли к **порталу 1С** выдавались заранее; при проблемах с сетью можно зайти **чёрной иконкой** (без «стартерового» сценария логина на портал для скачивания новой версии EDT).
- **EDT** — среда на базе **Eclipse**, на **Java**, долго стартует; для **объёмных типовых** конфигураций ориентир **не меньше 16 ГБ ОЗУ**; с **8 ГБ** на крупных конфигурациях можно не пытаться; на **небольших** учебных — работоспособно.

### Рабочая область и импорт

- При первом запуске — выбор **рабочей области** (расположение по смыслу не критично).
- Справочные окна можно закрыть («начать работу»).
- Проект создаётся **импортом** конфигурации из **информационной базы**, а не «с нуля», если конфигурация уже ведётся в конфигураторе (**рекомендуется** импортировать свою учебную конфигурацию).
- Важно выбрать **версию платформы**, соответствующую проекту (в примере у студентов **8.5.1**, у преподавателя — другая ветка **8.3.27** — нужно не смешивать).

### Подключение к ИБ

- Тип доступа: **информационная база**; пользователя часто нужно ввести **вручную** (не из списка).
- Пароль к **области** EDT можно задать простой (в демо — условно **1122**).
- Упоминались нюансы **WSL** и **лицензии** (смена параметров, запуск не под тем пользователем **usr1cv8** и т.д.) — при «невидимой» лицензии разбирать отдельно.

## Часть 3. Git в EDT

- В конфигураторе **нет** встроенного Git; в **EDT** — **есть** (вместе с напарником).
- Объявляется **общий проект**; создаётся **локальный репозиторий** (в т.ч. «создать репозиторий в родительской папке проекта»).
- Далее **Git** можно использовать **локально** и при необходимости связать с **GitHub** и т.д.

### Конфликт EDT и хранилища конфигурации

- Если конфигурация **подключена к хранилищу 1С**, с **EDT** типично **не работает** совместно (в записи явно: нужно **отключиться от хранилища** или обходить ограничение).
- Обход: **запуск конфигуратора из EDT** (контекстное меню приложения — **«Запустить конфигуратор»**), отключение от хранилища, затем **применение изменений** в EDT.
- Если конфигуратор/EDT мешают друг другу блокировкой — **закрыть** лишние сеансы.

### Сравнение и объединение при импорте

- При подтягивании конфигурации из ИБ используется **сравнение/объединение** с правилами второго источника; при «пустом» сценарии возможны сообщения **«изменений не найдено»** или затирание черновиков — при необходимости объекты (например, **перечисления**) создают заново.

## Часть 4. Практика метаданных: виды оплат

- Задача: развести смыслы **поступлений** и **списаний** денежных средств — добавлены **перечисления**: виды поступления ДС, виды списания ДС (оплата от покупателя, возврат от поставщика, оплата поставщику, возврат покупателю, прочее и т.д. по смыслу).
- **Перечисление** — не объектный тип; проверка — в **конфигураторе**, что значения на месте.

### EDT и конфигуратор

- **EDT** не заменяет платформу и конфигуратор: это **прослойка**, для работы нужны **установленная платформа** и доступ к **конфигуратору**; EDT использует конфигуратор под капотом.
- Плюс EDT для команд: **Git**, **ветки** — нет проблемы **захвата корня** хранилища.

## Часть 5. Ветвление (Git flow)

- Рекомендуемая логика близка к **Git Flow**: ветка **master** (или main) — то, что **отдаётся заказчику**; отдельные **feature**-ветки под задачи.
- Стратегии ИБ для ветки:
  - **файловая** — можно **копировать** файлы каталога ИБ;
  - **серверная** — можно **использовать ту же ИБ**, что и основная ветка, или создать **новую пустую**.
- Новая **пустая** ИБ: нет пользователей — перед переключением веток нужно **проиндексировать** и **зафиксировать** текущие изменения (**коммит**), иначе **master** остаётся «пустым» в смысле истории.
- Создание ветки: от **master**, опция **новая пустая информационная база** — задаётся путь (например, в «Документы»).
- После работы в feature: **зафиксировать** изменения, затем **слить** в **master** (в интерфейсе групповой разработки EDT); переключиться на **master**, выполнить **слияние** из feature, **применить** конфигурацию к ИБ.
- Не забывать повышать **номер версии** конфигурации при релизе.

## Часть 6. Отладка в EDT

- В Eclipse есть **перспективы**: **разработка**, **отладка**, **напарник**.
- Запуск клиента: в примере — **тонкий клиент** к файловой базе.
- **Точка останова** в модуле объекта — проведение документа попадает в отладчик; возможности шире, чем в классическом конфигураторе (с оговорками).
- Отладка из **WSL** / сервера: нужна **публикация** и режим отладки по **HTTP**; **EDT** в привязке к записи ориентируется на **HTTP-режим** отладки.
- После отладки — вернуть перспективу на **разработку**.

## Часть 7. «1С:Напарник» — запрос к коду

- В чате напарника: задача — добавить **движения по регистру накопления** (в записи — взаиморасчёты) для документа **«Приход товара»**.
- Напарник запрашивает **имя документа** и **контекст** (путь/открытый модуль); без контекста качество ниже.
- Возможны **ошибки** (имя регистра, опечатки); исправление через переименование метаданных и повторное применение; проверка — проведение документа и просмотр движений.

---

## Часть 8. Публикация репозитория и внешние инструменты

- **Локальный** Git можно **опубликовать** на **GitHub**; **свою** учебную конфигурацию в **public** обычно не страшно; **типовые** конфигурации — только **приватные** репозитории.
- **Альтернатива EDT — Cursor** (и аналоги): работа с **выгруженными файлами** конфигурации; у EDT **свой** формат проекта — не те же файлы, что у «текстовой» выгрузки.
- **Пайплайн** из EDT: помнить про **конвертацию** в формат конфигуратора и сборку **cf** / применение к ИБ перед дальнейшими шагами.
- **Cursor**: удобно для **расширений** и папок с лишними файлами (`.cursor`, описания агентов) — конфигуратор их не подтягивает как часть метаданных.
- Упоминались **нейросетевые** модели для генерации кода 1С и развитие **MCP** для форм; **агентская разработка** и **OpenSpec** — ориентир на **следующий семестр**.

## Часть 9. Разбор учебных проектов (фрагмент записи)

### Подсистемы и интерфейс

- Если **не созданы подсистемы** / объекты не включены в подсистемы, в интерфейсе «для пользователя» часть объектов **не видна**; раздел **«функции для технического специалиста»** показывает больше метаданных.
- Для роли **«Полные права»** у **администратора** нужна соответствующая **настройка** (в записи — «галочка» у администратора), иначе картина прав может быть неполной.

### Ошибки в движениях регистров

- Пример: документ **«Заявка на тур»**, движения по **оборотному** регистру («продажи туров») и по регистру **взаиморасчётов**.
- Ошибка: для **оборотного** регистра **нет** «вида движения» в том виде, как для **остаточного** — нельзя смешивать модели; нужно согласовать тип регистра и код проведения.
- Отладка: по тексту ошибки (**номер строки** в модуле) — **точка останова**; для серверной отладки — включить **режим отладки** у **сервиса** (в записи правили **default.vrd** / параметры публикации), подключение **отладчика к серверу**.

### Организация отчётности по спринту

- Ожидание: отчёт по спринту согласован с планом (**что добавили/убрали**); гибкий подход (**agile**): дорабатывать объём итеративно.
- К следующему сроку — более чёткая **MDL** / описание бизнес-процесса, можно в виде **user story**; у одной из групп (туроператор) можно взять **образец оформления**.

## Резюме

1. **EDT** — тяжёлая IDE, импорт своей ИБ, верная **версия платформы**.  
2. **Напарник** — токен из таблицы, параметры среды.  
3. **Git в EDT** — локальный репозиторий, ветки, коммит, слияние в master, версия конфигурации.  
4. **Хранилище 1С** и **EDT** одновременно — конфликт; отключение от хранилища или обход через конфигуратор.  
5. **Отладка** — перспективы, тонкий клиент, HTTP-режим для сервера/WSL.  
6. **Напарник** — генерирует код с проверкой контекста и метаданных.  
7. **Проекты** — подсистемы, роли, корректные **движения** по типу регистра, серверная отладка.
